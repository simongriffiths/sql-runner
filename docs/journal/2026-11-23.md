## S1. Dedicated keychain mechanics

### What was run

`S1-keychain/main.swift` builds `s1-spike`, a small Swift binary. It uses a test keychain, `~/Library/Keychains/road-spike.keychain-db`. It stores that keychain's password in the login keychain under the service `road-secrets-spike/keychain-password`. Reads print only the length and a SHA-256 prefix, never the value.

Build and run, on macOS 27.3 with Swift 6.4.2:

```
swiftc -swift-version 5 -O main.swift -o s1-spike
./s1-spike init | settings | lock | unlock | add | read | update | delete | destroy
```

By default the binary turns off user interaction with `SecKeychainSetUserInteractionAllowed(false)`. A read that would need a prompt therefore fails instead of waiting. Setting `S1_ALLOW_UI=1` allows prompts.

### Outcome

These steps pass:

- Create the keychain with `SecKeychainCreate`, set it never to lock, and add it to the user search list.
- Store the keychain's password in the login keychain. Lock the keychain, then unlock it with that password.
- Add, read, update and delete a generic-password item in the keychain. The item's access list is built with `SecAccessCreate`. `security dump-keychain -a` shows that the decrypt rights name only `s1-spike`.
- Do all of these from this Claude Code session in the desktop app with prompts turned off. None needed a prompt.

The deprecated APIs work. The dedicated keychain path is viable so far, so no fallback to the login keychain is needed yet. Two details had to be fixed:

1. `SecKeychainSetSettings` rejects a `lockInterval` of `UInt32.max` with -25293 (`errSecAuthFailed`). Using `INT_MAX`, which is what `security set-keychain-settings` uses, works.
2. The new keychain is unlocked explicitly before its settings are changed.

Two other findings:

- **Access follows the code signature, not the path.** A byte-identical copy of the binary at another path could read the item with no prompt.
- **A rebuild locks the binary out of the login-keychain item as well.** After a rebuild with prompts turned off, the first read failed. It failed on the keychain password in the login keychain, before it reached the dedicated item. It failed with -25293 (`errSecAuthFailed`), not `errSecInteractionNotAllowed`. A rebuild therefore causes at least two "Always Allow" prompts: one for the login-keychain item and one for each item in the dedicated keychain.

### Waiting for Simon

These steps need a person at the Mac mini's desktop. The binary has already been rebuilt, so the prompts are due.

1. Run `S1_ALLOW_UI=1 ./s1-spike read`. Count the prompts. Note whether any prompt asks for the dedicated keychain's own password, which nobody knows. Click Always Allow on each, then run the command again and confirm there is no prompt.
2. After a restart, run `S1_NO_UNLOCK=1 ./s1-spike settings`, which should show `unlocked=false`. Then run `./s1-spike read`, which should succeed with no prompt.
3. Run `./s1-spike destroy`.

If step 1 asks for the dedicated keychain's password, fall back to the login keychain as section 12 describes.

### Decision for the build and spec changes

- Section 9.2: say that a rebuild raises one prompt for the login-keychain item that holds the keychain password, plus one for each item that is read. Do not say "exactly one".
- Section 9.3: also treat `errSecAuthFailed` (-25293) from a read as "Keychain not available", and exit 4. That is the status a refused access-list check returns when prompts are not possible.
- When building `init`: unlock the keychain right after creating it, and use `INT_MAX` for the lock interval.

## S2. Re-saving SQLcl connections

### What was run

`S2-sqlcl/s2_spike.py` drives SQLcl 26.1 through standard input only. It masks every generated password and counts any that appear in SQLcl's raw output. It ran only against roadkitdb, connecting as `roadkit_admin`. It:

- created the users `RS_SPIKE` and `RS_SPIKE_TARGET`, each with `create session` only, plus `alter user RS_SPIKE_TARGET grant connect through RS_SPIKE`.
- created the saved connections `rs_spike` and `rs_spike_proxy` (`RS_SPIKE[RS_SPIKE_TARGET]`).
- tested the candidates in section 12, then cleaned up.

Every password was in the `Adjective.Noun.nnn` format. The steps are `setup`, `resave`, `bulk`, `discover`, `history` and `cleanup`. `probe`, `probe2` and `visibility` are the diagnostics used along the way.

### Outcome

**Candidate 1 fails.** Candidate 1 is `TNS_ADMIN` set to the connection's wallet directory, with `conn -save <name> -savepwd ...`. Every connect retried for about 65 seconds, then failed with `ORA-12529: TNS:connect request rejected based on current filtering rules`. The wallet in `~/.dbtools/connections/<id>/` is not used when it is reached through `TNS_ADMIN`. The `sqlnet.ora` there points at `?/network/admin`.

**Candidate 2 works.** Candidate 2 is `-cloudconfig <wallet.zip>`. The zip was built from that same wallet directory and kept at mode 0600 in `/private/tmp`; it was deleted afterwards. The command was:

```
conn -cloudconfig <zip> -save <name> -savepwd -replace <user>/<pwd>@roadkitdb_medium
```

Each re-save took about 1.9 seconds on its own.

**Failures are invisible with the spec's prefix lines.** With `set feedback off`, a failed connect prints nothing, SQLcl exits 0, and `show user` returns `""`. With `set feedback on`, SQLcl prints "Connection failed", including the `ORA-` line. A wrong password tested both ways gave the same result. `set echo` makes no difference.

Discovery found 162 `LIVEHUB_DEPLOY` connections, all of them proxy connections:

- 17 on `roadkitdb_medium`, as the spec says.
- 145 on `quoratedb_medium`. The spec says 125.

The user names are stored in lowercase, for example `livehub_deploy[av_acc]`. At 0.44 seconds each, re-saving the 145 on quoratedb should take about 64 seconds.

Cleanup: both users were dropped, and all 19 `rs_spike*` connections and their folders under `~/.dbtools/connections` were deleted. Afterwards `dba_users` held no `RS%SPIKE%` users, and `connmgr list` held no `rs_spike` names.

### Decision for the build and spec changes

- Section 8: replace `set feedback off` with `set feedback on`. As a second check, run `show user` after every `conn` and treat an empty user as failure. Do not rely on `ORA-`/`SP2-` lines or the exit code alone.
- Section 8: do not set `TNS_ADMIN` to the connection's wallet directory. Re-save with `conn -cloudconfig <zip> -save <name> -savepwd -replace`. Build the zip once per database from the connection's wallet directory. Keep it at mode 0600 in a private temporary directory and delete it on exit.
- Always pass `-replace`. Treat "already exists" in the output as failure.
- A re-save rewrites the whole connection from the arguments given: user, `@<tns alias>` and wallet. A wallet zip is per database, so re-save one database at a time.
- Discovery: compare user names case-insensitively, because SQLcl stores them as typed (`livehub_deploy[...]`).
- Section 12 and the operating notes: change the quoratedb count from 125 to 145 and the time estimate to about 64 seconds.
- The real re-save of `LIVEHUB_DEPLOY` connections has not been run, on purpose.

## Spec v1.6: an add command, and every other command takes only the key (27 November 2026)

### What changed

- `set`, `sync`, `get`, `copy`, `check` and `delete` now take only the key, as `list` prints it, and they work from any folder.
- The new `add` command creates an entry. It takes `--app`, `--env`, `--kind` and `--name`, plus the details the kind needs the first time.
  - It never asks a question, and it prints the key when it succeeds.
  - A db user's current password is read from standard input, with no prompt and no echo.
  - `add` refuses a key that already exists.
- `set` on a missing key exits 3 and points to `add`.
- A principal's project folder is `--project`, else the stored folder, else `$ROAD_PROJECTS/<app>`, else `~/Projects/<app>`.
- The spec is now v1.6.

### Decisions

- **`set` keeps two flags.** `--via-admin` and `--yes` stay on `set` for db keys. `--via-admin` is the way to recover a key whose stored password no longer works. `--yes` keeps the confirmation rule for several connections: at a terminal `set` still asks, and otherwise it needs `--yes`.
- **`add` needs `--yes` for several connections.** It never asks, so it exits 2 without `--yes` when more than one connection would be re-saved.
- **`add` refuses before it reads anything.** It applies the production guard and the ADMIN naming rule before reading standard input. Neither check reads a password.
- **Status lines go to standard error.** Progress, warnings and the success line of `set` and `add` now go to standard error. `add` prints only the key on standard output, so a script can capture it.
- **The current folder no longer matters.** `Dependencies.gitRoot` is removed, because the project folder no longer comes from the current folder's git repository.
- **More build retries.** `make road-secrets-test` and the installer now try the build up to three times. During this work the toolchain's "plugin for module TestingMacros not found" failure happened twice in a row.

- `swift test`: 57 tests in 14 suites pass. New tests cover:
